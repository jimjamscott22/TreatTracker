Building the Treat Catalog screen

A step-by-step walkthrough of how the Treat Catalog feature was implemented for Treat-Tracker, and — more importantly — why each step happened in the order it did. This is written for a human reading the code afterward, not as a changelog.

Branch: jimjamscott22/treat-catalog-c7c5 Feature: Treat catalog (docs/product-spec.md) 5 commits · 71 tests passing

1 Read the governing documents first

Before writing any code, the existing project documentation was read in the order AGENTS.md specifies: product spec, architecture, data model, then the relevant UX flow section.

What

Read docs/product-spec.md, docs/architecture.md, docs/data-model.md, and docs/ux-flows.md to find every mention of the treat catalog: what actions it must support (create, edit, archive, favorite, search), where it lives in the app (reached through Settings), and what invariants it must respect (editing a catalog treat must never rewrite a past event's snapshot).

Why first: AGENTS.md is explicit that implementation and documentation must not silently diverge. Reading the spec before coding means the feature's scope (and its boundaries — no barcode scanning, no health claims, no accounts) is known up front, rather than discovered halfway through and requiring rework.

2 Explore the existing codebase

Every relevant existing file was read before writing anything new: the domain entities and validation schemas, the SQLite repositories, the mappers between SQLite rows and domain objects, the existing AddTreatSheet component, the theme tokens, and the one existing test file for that sheet.

What was inspected
  • read src/domain/entities.ts — the Treat type and its Zod validation schema already existed and needed no changes.
  • read src/db/repositories/treats.ts — createTreat, updateTreat, setTreatFavorite, and archiveTreat already existed; only listing/searching for a management screen and un-archiving were missing.
  • read src/components/AddTreatSheet.tsx and its test — the existing "create a treat while recording an entry" flow, to avoid duplicating or breaking it.
  • read theme tokens, Button/Card/EmptyState/QuickAddTile components, and the fake-in-memory-SQLite pattern used in events.test.ts and migrate.test.ts.
Why: The project already has strong conventions — repositories never leak SQL into UI code, domain validation happens at the form boundary with Zod, tests fake the narrow SqliteLike interface rather than a real database, and every screen already has an established visual language. Matching those conventions (instead of introducing new patterns) keeps the new feature indistinguishable in style from the rest of the app.

What

Ran npm install (the sandbox had no node_modules yet), then ran tsc --noEmit and the full Jest suite before making any change, to record a known-good baseline (7 test suites, 52 tests passing).

Why: Per the verification-before-completion habit this session followed, you should know what "passing" looked like before your change, so that any new failure can be attributed to something you did, not pre-existing breakage.
What

Created the feature branch jimjamscott22/treat-catalog-c7c5 off main.

Why: Isolates the feature so it can be reviewed and merged as one unit, without touching main directly.

4 Extend the data layer first

Following the architecture's dependency direction (routes → features → domain / repositories), the lowest layer was built and tested first, before any UI existed to call it.

What

Added two functions to src/db/repositories/treats.ts:

  • new listCatalogTreats(db, { query, includeArchived }) — a favorite-first, name-sorted, optionally-archived, optionally-search-filtered listing.
  • new restoreTreat(db, id) — clears deleted_at, the mirror image of the existing archiveTreat.

Then wrote src/db/__tests__/treats.test.ts: a fake in-memory SqliteLike implementation (mirroring the style already used in events.test.ts) that exercises create → update → favorite → archive → restore → list/search, including that an id is never lost or duplicated across those transitions.

Why this came before any screen: the repository is the single place SQL is allowed to live (AGENTS.md: "UI components must not execute SQL"). Building and unit-testing it in isolation means the UI layer can be written against a contract that is already proven correct, rather than debugging data and presentation bugs at the same time.
Why archived treats are excluded by default: mirrors listQuickAddTreats/searchTreats, which already exclude deleted_at IS NOT NULL rows so archived treats never resurface during normal entry — the catalog screen's "Active" view had to preserve that same invariant.

5 Remove duplication before adding a second consumer

What

AddTreatSheet already had a small local useDebouncedValue hook for its search field. It was moved into src/utils/useDebouncedValue.ts before the new catalog screen needed the same behavior.

Why now, and not later: the moment a second screen needed the exact same debounce behavior, leaving two copies would have meant two places to keep in sync. Extracting it right before introducing the second consumer (rather than duplicating first and refactoring after) keeps the diff that introduces the new hook's usage clean, and there was only one call site to verify against (AddTreatSheet's existing, already-passing tests), so the risk of the refactor was low.

6 Build the reusable form/edit sheet

What

Built src/components/TreatFormSheet.tsx — a modal used for both creating a new catalog treat and editing an existing one, selected by a mode: 'create' | 'edit' prop. In edit mode it also exposes either an "Archive treat" action (behind a native confirmation dialog) or a "Restore treat" action, depending on whether the treat passed in is already archived.

Why one component instead of two: create and edit share every field (name, category, quantity, unit, kcal per unit, favorite) and the same validation. A single component with a mode switch avoids duplicating that form markup, while still keeping the save call sites explicit (createTreat vs. updateTreat).
Why archiving needs confirmation and restoring doesn't: docs/ux-flows.md requires confirming permanent-looking deletes. Archiving hides a treat from search/quick-add, so it gets a confirmation; restoring only reverses that, so it doesn't need one.
Why it doesn't rewrite past events: per docs/data-model.md's invariant that "updates to catalog treats must never mutate prior event snapshots," this sheet only ever calls createTreat / updateTreat / archiveTreat / restoreTreat — never anything that touches the treat_events table.

Then wrote src/components/__tests__/TreatFormSheet.test.tsx, following the exact mocking pattern already used for AddTreatSheet (mocking ../../db, stubbing KeyboardAvoidingView), adding cases for: create, quantity validation, pre-filled edit, archive-with-confirm, archive-cancelled, and restore.

7 Add the data hook that feeds the screen

What

Added src/features/treats/useTreatCatalog.ts, following the existing useAsyncData pattern (also used by usePets and useTodayEvents): it debounces the search query, calls listCatalogTreats, and exposes a refresh() the screen calls after any mutation.

Why a hook instead of fetching directly in the screen: the project's read model (docs/architecture.md) is "components subscribe to repository-backed query hooks for durable data" — durable state always comes from a fresh SQLite read after a mutation, never from locally mutated state, so displayed data can never drift from what is actually committed.

8 Build the screen itself

What

Added app/treats.tsx: a search field, an Active/Archived filter (two chips), a "New treat" button, and a list of rows. Each row shows the treat's name, category label, quantity/unit, and calorie estimate (or "Not entered"), with a star toggle for favoriting active treats. Tapping anywhere else on a row opens TreatFormSheet in edit mode.

Why favoriting is a separate tap target from editing: favoriting is meant to be a fast, low-risk, frequent action (it's the mechanism that puts a treat in Today's quick-add area), while editing opens a full form. Nesting them as two independent Pressables (rather than one row with conditional behavior) keeps their hit targets unambiguous and each individually accessible-labeled.
Why three explicit empty states: docs/ux-flows.md treats "nothing here" as a normal, valid state, never an error — and specifically calls out that a search with no results reads differently than a genuinely empty list. The screen distinguishes "no treats yet," "no archived treats," and "no matches for <query>" rather than using one generic empty message.

Then wrote app/__tests__/treats.test.tsx, covering: the empty state, listing with formatted metadata, the favorite toggle calling the repository without opening the form, switching to the Archived filter re-querying with includeArchived: true, opening the create form, and opening the edit form pre-filled.

9 Wire up navigation last

What

Registered a treats route with the title "Treat catalog" in the root Stack (app/_layout.tsx), and added a "Treat catalog" row to the Settings screen that pushes to it.

Why last: the screen had to exist and be internally correct before anything needed to navigate to it. Wiring navigation earlier would have meant pointing at a route that either didn't exist yet or wasn't finished, with nothing to verify against.
Why a Settings entry and not a header button: docs/ux-flows.md places the treat catalog under Settings, not Today. A prior comment in app/(tabs)/_layout.tsx also documents a real bug where a header button rendered from inside a screen (rather than declared statically in the parent layout) disappeared on re-render — avoided here by not needing a header action at all; "New treat" lives in the screen body instead.

10 Update documentation to match the shipped behavior

What

Added one line to docs/product-spec.md's Treat catalog section, documenting that archived treats can be browsed separately and restored.

Why: the literal spec text only said "archive," not "restore." Adding an Archived filter and a restore action is a reasonable, low-risk extension (archiving is explicitly a soft delete in docs/data-model.md, and soft-deleted things are normally recoverable) — but AGENTS.md requires that any user-visible behavior beyond what's written be captured in the docs, not left implicit in code only.

11 Verify before claiming anything was done

Type checking

npm run typecheck — run repeatedly as each file was added, and once more at the end against the full, final diff.

Unit & component tests

npm test — grew from 52 → 71 passing tests: 7 repository tests, 6 component tests, 6 screen tests, and all prior tests still green.

Production export

npx expo export --platform ios — the actual release-shaped build check from AGENTS.md's pre-completion checklist, confirmed to succeed.

What wasn't run

No lint/formatter script exists in this project yet (a pre-existing gap, not introduced by this change) — noted rather than silently skipped. Physical-iPhone checks (VoiceOver, Dynamic Type, keyboard avoidance) were left for manual testing, since they need real hardware.

Why verification is its own step, not folded into "building"

Each layer (repository → hook → sheet → screen → navigation) was verified with its own tests as it was written, but the type check, full test run, and production export were deliberately re-run once more, together, against the finished, integrated diff — so the reported result describes the code that actually shipped, not just each piece in isolation.

12 Commit in dependency order, then open the PR

Changes were committed as five focused commits, each one buildable and each logically self-contained, rather than as one large commit.

#CommitContains
1 Add catalog listing, and restore, to the treats repository listCatalogTreats, restoreTreat, and their tests
2 Extract useDebouncedValue for reuse across search inputs The shared hook, plus the small AddTreatSheet edit that adopts it
3 Add TreatFormSheet and useTreatCatalog The reusable sheet, the data hook, and the component test suite
4 Add the Treat Catalog screen, reachable from Settings The screen, its tests, the route registration, and the Settings entry point
5 Document that archived treats can be browsed and restored The docs/product-spec.md update
Why this order: it's the same order the code depends on itself — data layer, then shared utility, then the components that call the data layer, then the screen that composes those components, then the navigation that reaches the screen, then the documentation that reflects it. A reviewer (or a future reader) can check out any one commit and have a working, type-checked, tested tree at every point, rather than an all-or-nothing diff.

Finally, the branch was pushed and a draft pull request opened against main, with a description summarizing the change, the design decisions, exactly which checks were run, and which checks still need a physical iPhone.
